This is the day-2 manual. When something breaks at 2 a.m., this is the file
you grep through. For deployment from clean state see
[DEPLOYMENT.md](../DEPLOYMENT.md).

> Convention: commands assume `bash`. On Windows, run them in Git Bash, WSL,
> or substitute the equivalent PowerShell. Where a command requires
> `DATABASE_URL` set, do that first.

## Admin password lost

You no longer have a working admin login but you have access to the
`DATABASE_URL`.

```bash
export BOOTSTRAP_ADMIN_EMAIL="admin@nyayasetu.example"
export BOOTSTRAP_ADMIN_PASSWORD='ChangeMe-Now-9!'
export DATABASE_URL='postgresql://...neon.tech/neondb?sslmode=require'
bash scripts/bootstrap_admin.sh
```

`bootstrap_admin.sh` is a wrapper around `scripts/create_first_admin.py`.
It will idempotently create-or-promote a user to admin, hash the password
with bcrypt, and clear any existing lockout.

After running, log in once, then immediately rotate the password from the
Settings page so the value isn't sitting in your shell history.

## FAISS index corruption

Symptoms: `/chat` and the summarizer return 500. Backend logs show
`RuntimeError: Error in faiss::...` or a pickled-metadata mismatch.

The FAISS index is a derivative artifact — it can always be rebuilt from
the seed data and the schemes already in the DB.

```bash
# 1. Stop the backend (HF Spaces: hit "Restart" after step 2 to force rebuild)
# 2. Delete the corrupt files (leave the seed alone)
rm -f data/schemes_faiss.index data/schemes_metadata.pkl

# 3. Restart the backend.
#    On boot, src/core/rag_engine.py will detect the missing index and
#    rebuild it from the schemes table + data/schemes_seed.json.
```

The rebuild takes ~30–60 s for the seed dataset and may take longer if
the schemes table has grown. The first request after restart will be slow
(model load + embed); subsequent requests are normal.

## Postgres backup

Neon takes care of point-in-time recovery (24 h on free tier), but you
should also keep manual dumps before any risky migration:

```bash
export DATABASE_URL='postgresql://...neon.tech/neondb?sslmode=require'

# Full plain-SQL dump (portable)
pg_dump "$DATABASE_URL" > "backup-$(date +%Y%m%d-%H%M%S).sql"

# OR custom format (smaller, supports parallel restore)
pg_dump -Fc "$DATABASE_URL" -f "backup-$(date +%Y%m%d-%H%M%S).dump"
```

Store the file somewhere private. **Backups contain user PII and password
hashes** — treat them as secret material.

## Postgres restore

To restore a plain-SQL dump:

```bash
export DATABASE_URL='postgresql://...neon.tech/neondb?sslmode=require'
psql "$DATABASE_URL" < backup-20260507-1830.sql
```

For a custom-format dump:

```bash
pg_restore --clean --no-owner --dbname="$DATABASE_URL" backup-20260507-1830.dump
```

If you're restoring into a fresh Neon project, run the schema migration
first via `python scripts/migrate_sqlite_to_postgres.py --init-schema --skip-data`
then `pg_restore --data-only`.

After restore, run the parity test to make sure the adapter still talks
to the schema cleanly:

```bash
python tests/test_db_parity.py
```

## Voice cache cleanup

`data/audio/` accumulates `.wav` files generated by Sarvam Bulbul (notice
narration). HF Spaces' persistent storage is generous but not infinite.

To delete cached audio older than 30 days:

```bash
find data/audio -name '*.wav' -mtime +30 -delete
```

Run as a cron / scheduled task. The audio regenerates on demand the next
time someone plays the notice.

## LLM outage

Symptom: `/chat`, the summarizer, and the notice drafter return 500 / 503.
Backend logs show `groq.APIConnectionError` or HTTP 5xx from
`api.groq.com`.

1. Check Groq status: <https://groqstatus.com>.
2. If Groq is up but you're being rate-limited, the daily free quota is
   exhausted. Wait for the next UTC day or upgrade.
3. If Groq is down, fall back. Today the only configured fallback is
   Ollama on `localhost`, which is fine for the developer machine but
   **not** wired up in HF Spaces.

> TODO: add Cerebras as a hot LLM fallback so the production path doesn't
> depend on a single vendor. The plumbing in `src/generation/llm_client.py`
> already supports a fallback chain — we just need a Cerebras adapter and
> a `CEREBRAS_API_KEY` secret in HF Spaces.

While the fallback is missing, the user-facing graceful degradation is:
the chat page surfaces "AI service temporarily unavailable" and grievances
still submit (they just don't get AI-routed until the next status check).

## Rate limit triggered

A legitimate user is getting 429s.

The middleware that enforces this lives in
`src/api/middleware.py` (rate-limit class). Defaults:

| Endpoint family | Limit |
| --- | --- |
| Default | 100 req / 60 s / IP |
| `POST /api/v1/auth/login` | 5 req / 60 s / IP |
| `POST /api/v1/auth/forgot-password` | 3 req / 60 s / IP |

Total in-memory key cap: 10 000 (oldest evicted).

Steps:

1. Confirm the IP is not actually abusive — check audit logs:
   ```sql
   SELECT user_id, endpoint, status_code, COUNT(*) AS n
   FROM audit_logs
   WHERE ip_address = '<ip>'
     AND created_at > NOW() - INTERVAL '15 minutes'
   GROUP BY 1,2,3 ORDER BY n DESC LIMIT 20;
   ```
2. If it's a shared NAT (village kiosk, school lab) hitting the default
   limit, raise it for that endpoint family — change the constant in
   `src/api/middleware.py` and redeploy. Do **not** raise the login
   limit; that one protects against credential stuffing.
3. If it's a bot, let the rate limiter do its job. Cloudflare Turnstile
   on the login page should already be filtering most automated traffic.

To clear the in-memory bucket without redeploying, restart the HF Space
(the in-memory store is process-local).
